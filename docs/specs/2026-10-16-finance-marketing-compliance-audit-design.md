## 0. 核实声明（先读这一节）

本文档中的所有法规条款、文号、数据源入口、真实案例，均在 **2026-10-16 实际联网核实**，来源见 §12 与附录 A。**没有一条是推测或编造的。**

本文档中所有涉及系统性能的数值（准确率、召回率、误报率、审核耗时）**全部是占位符**，写成 `{待测}`。这些数字必须在第 5–6 周的评测阶段由真实运行产生，**在此之前禁止出现在简历、面试或任何对外材料中**。

本项目的核心设计原则是：**每一个对外声称的数字都必须能回答"怎么来的"。** 这是与常见"包装型"简历项目的根本区别，也是本项目的主要竞争力。

## 1. 问题定义

### 1.1 业务场景

金融机构（银行、公募/私募基金、消金、保险、券商）在对外投放营销物料时——App 落地页、微信推文、产品详情页、宣传海报、直播话术、短信、宣传推介材料——必须遵守多层级法规。发布前的合规审核目前主要依赖合规专员人工逐条比对法条。

### 1.2 真实痛点（有法规依据）

**痛点一：纯关键词规则误报率高，因为法规本身带豁免条款。**

《广告法》第九条第（三）项禁止使用"国家级""最高级""最佳"等用语。但市场监管总局 2023 年发布的《广告绝对化用语执法指南》明确了**三种豁免情形**：

1. 仅表明服务态度、经营理念或主观愿望；
2. 仅表达目标追求；
3. 与商品性能质量无直接关联且不误导消费者。

这意味着"追求卓越品质"（目标追求）与"最高收益率"（性能承诺）在关键词层面完全同形，在合规层面一个放行一个拦截。**纯词库规则无法区分，只能全拦，于是产生大量误报。** 这是本项目引入 LLM 语义层的根本理由——不是"因为 AI 很火"，而是因为法规的豁免逻辑本身就需要语境判断。

**痛点二：违规表述的法规清单极长，人工比对成本高。**

仅《关于加强私募投资基金监管的若干规定》第六条就列举了"安全、保本、零风险、收益有保障、高收益、本金无忧、预期收益率、目标收益率、基准收益率"等一长串禁用表述；基金宣传推介材料规范另列举了"坐享财富增长、安心享受成长、尽享牛市、欲购从速、申购良机、净值归一、名列前茅、位居前列"等。合规专员需要记住并比对分散在多部法规中的数十类禁止情形。

**痛点三：隐性违规无法用词表覆盖。**

真实处罚案例中大量违规并不含任何禁用词。例如"宣传推介材料明确载明该基金的预期年化收益"——"预期年化收益"本身不在禁用词表里，但在私募基金语境下被监管认定构成"承诺最低收益"（见附录 A 案例 4）。这类判定依赖业务语境理解。

### 1.3 目标用户与角色

| 角色 | 职责 | 与系统的交互 |
|---|---|---|
| **营销/产品运营** | 制作物料，提交审核 | 粘贴文案 → 看到红黄绿结论与改写建议 → 修改后重新提交 |
| **合规专员**（核心用户） | 复核 AI 判定，做最终放行/拦截决定 | 处理黄标队列 → 逐条确认或推翻 → 标记误报 |
| **合规负责人** | 维护法规库与规则库，看审核统计 | 更新法条 → 查看误报率趋势 → 审阅纠偏队列 |

**MVP 只服务"合规专员"这一个角色。** 营销侧提交界面和负责人看板在 §2.2 列为非目标。理由：单角色闭环足以验证核心价值，多角色会引入权限、工作流引擎等与项目目标无关的复杂度。

### 1.4 成功标准（可验证）

项目达成以下四条即算成功，全部可客观检验：

1. **数据资产**：产出 ≥ 120 条带条款级标注的真实评测样本，每条可溯源到具体处罚文号或法规条款。
2. **系统能力**：双轨引擎在评测集上的**高危类召回率**与**加权成本**显著优于纯规则基线和纯 LLM 基线（具体阈值在评测前预注册，见 §7.6）。
3. **可演示性**：一个可运行界面，输入真实文案，30 秒内完成高亮溯源 + 条款引用 + 一键改写的全流程演示。
4. **可复现性**：陌生人 clone 仓库后，按 README 步骤能复现评测报告中的每一个数字。

## 2. 范围

### 2.1 MVP 包含

- 文本单模态输入（复制粘贴 / 上传 txt / 上传 md）
- 法规知识库（结构化条款 + 轻量检索）
- 双轨审核引擎（规则层 + LLM 语义层 + 融合分级）
- 违规点高亮溯源，附违反的具体条款原文
- 一键智能改写（Auto-Fix）
- 风险三级分档（高危拦截 / 中危人工复核 / 合规放行）
- HITL 误报纠偏，纠偏记录落盘可导出
- 评测流水线与可复现评测报告
- 审核报告导出（Markdown / JSON）

### 2.2 明确的非目标（写进 PRD，面试时主动讲）

主动声明非目标是 B 端产品成熟度的标志。以下功能**本项目刻意不做**，每条附理由：

| 非目标 | 不做的理由 |
|---|---|
| **图像 OCR / 音视频 ASR 接入** | 多模态会把工程量翻倍，而项目核心价值（双轨判定 + 真实评测）不依赖它。附件文档把它列为一等公民是错误的范围判断。架构上预留 `ContentAdapter` 接口，未来可加。 |
| **模型微调 / 训练** | 无标注数据规模支撑，且违反 YAGNI。提示词与规则库迭代的 ROI 远高于微调。 |
| **多角色权限与工作流引擎** | 见 §1.3。单角色闭环已足以验证价值。 |
| **高并发与实时流式处理** | 面试常问的性能问题，用 §6.6 的分级策略与实测延迟数据回答，而不是真的去实现消息队列。 |
| **给出最终合规结论** | **法律与产品双重红线。** 系统只输出"建议"，发布权与拦截权始终在人工合规官手中。这不是能力不足的托词，是 B 端 AI 的正确定位。 |
| **英文 / 跨境合规（GDPR、SEC 营销规则）** | 法规体系完全不同，超出范围。 |
| **对接企业内部 CMS / OA** | 需要真实企业环境，无法在个人项目中验证。 |

### 3.2 违规类型 Taxonomy

**一级分类 = R3（银发〔2019〕316 号）第三条（四）至（十一）项的八项禁止性规定，一项对一个 C 编号。** 二级分类 = 从 R4–R7 的具体细则中，把每一级类展开成"可直接对照文案判定"的情形。

R3 第三条共十一项，其中（一）至（三）是**正向义务**（机构应建立内控制度、监测机制、监督合作方），不是审核文案时能判定的违规类型，故不纳入 taxonomy；（四）至（十一）是**禁止性规定**，构成本项目的八个一级类：

| 一级类 | R3 第三条项号（2026-10-16 经央行官网原文逐字核实） | 二级类来源 |
|---|---|---|
| C1 | （四）不得非法或超范围开展金融营销宣传活动 | R3 自身（资质要求章节） |
| C2 | （五）不得以欺诈或引人误解的方式对金融产品或金融服务进行营销宣传 | **R4 R5 R6 R7 展开为 C2.1–C2.12** |
| C3 | （六）不得以损害公平竞争的方式开展金融营销宣传活动 | R3 自身 + R1 |
| C4 | （七）不得利用政府公信力进行金融营销宣传 | R5（以登记备案/托管/政府出资名义增信） |
| C5 | （八）不得损害金融消费者知情权 | R7（业绩登载规范）、R8（可识别性） |
| C6 | （九）不得利用互联网进行不当金融营销宣传 | R8 |
| C7 | （十）不得违规向金融消费者发送金融营销宣传信息 | R3 自身 |
| C8 | （十一）不得开展法律法规和国务院金融管理部门认定的其他违法违规金融营销宣传活动 | 兜底类 |

> **措辞勘误**：（十）项官方原文为"金融营销**宣传**信息"，人民银行官方答问中简写为"金融营销信息"。入库以原文为准。

**"细则展开"的机制，以 C2 为例：**

R3（五）的原文是宽泛的原则性规定——"不得对资产管理产品未来效果、收益或相关情况作出保证性承诺，明示或暗示保本、无风险或保收益；不得使用偷换概念、不当类比、隐去假设等不当营销宣传手段"。这句话**没法直接拿去审文案**："明示或暗示保本"里，什么算暗示？

R5《关于加强私募投资基金监管的若干规定》第六条把它落到了具体表述：

> "夸大、片面宣传私募基金，包括使用**安全、保本、零风险、收益有保障、高收益、本金无忧**等可能导致投资者不能准确认识私募基金风险的表述，或者向投资者宣传**预期收益率、目标收益率、基准收益率**等类似表述"

R4《私募投资基金监督管理条例》第三十二条再补一层："向投资者承诺投资本金不受损失或者承诺最低收益"。R7 基金宣传推介材料规定又补充了公募侧的"预测基金的投资业绩""登载单位或者个人的推荐性文字"等。

于是从 R3（五）这一条，展开出 C2.1–C2.12 十二个**可逐字对照判定**的二级类。展开的结果就是附录 B 的四层词库——**每个词条都能指回具体法规，没有一个自造词。**

**这个设计带来三个实际好处：**

1. **每个标签都有法规出处。** 面试官问"你的违规分类怎么定的"，答案是"照 316 号文第三条（四）至（十一）项逐条映射，二级从私募条例、若干规定、销售办法的细则展开"，而不是"我自己归纳的"。
2. **解释了为什么 §4.2 的 `violated_clauses` 是数组。** 一个二级类往往同时触犯多部法规——C2.1 就同时来自 R3（五）、R4 第三十二条、R5 第六条。单值字段存不下。
3. **法规更新时的响应路径是确定的。** 新增一条红线 = 加一条 `clause` 记录 + 挂到已有 C 类下，或新增一个 C2.x 子类。不需要改代码、不需要重训模型——这正是"监管政策突然变了怎么快速响应"这个问题的答案。

```
C1 非法或超范围开展金融营销宣传
C2 以欺诈或引人误解的方式营销宣传          ← 核心类别，样本占比预计最高
   C2.1 保本保收益承诺（明示或暗示保本、无风险、保收益）
   C2.2 过往业绩虚假或夸大表述
   C2.3 引用不真实、不准确的数据和资料
   C2.4 隐瞒限制条件 / 隐去假设
   C2.5 预测投资业绩（预期收益率、目标收益率、基准收益率）
   C2.6 偷换概念、不当类比
   C2.7 绝对化用语（广告法第九条第三项）
   C2.8 风险误导性表述（安全、保本、零风险、收益有保障、高收益、本金无忧…）
   C2.9 片面强调集中营销时间（欲购从速、申购良机）
   C2.10 误导性表述（净值归一）
   C2.11 无客观证据的排名表述（业绩稳健、名列前茅、位居前列、唯一）
   C2.12 登载单位或个人的推荐性文字
C3 以损害公平竞争的方式营销宣传
   C3.1 恶意诋毁竞争对手 / 损害同业信誉
   C3.2 不当评比、不当排序
   C3.3 冒用或擅用他人商标、字号、宣传册页
C4 利用政府公信力进行金融营销宣传
   C4.1 利用监管审核或备案程序误导消费者认为政府提供保证
   C4.2 以登记备案、金融机构托管、政府出资等名义增信
   C4.3 对未经审核或备案的产品预先宣传促销
C5 损害金融消费者知情权
   C5.1 风险提示缺失或不显著（"大字吸睛、小字免责"）
   C5.2 业绩登载不符合规范（如基金合同生效不足 6 个月登载过往业绩）
   C5.3 关键费用、限制条件未披露
C6 利用互联网进行不当金融营销宣传
C7 违规向金融消费者发送金融营销信息
C8 其他违法违规金融营销宣传
```

**MVP 只做 C1–C5**（C6–C8 依赖渠道/发送行为数据，纯文本审核判不了）。这个裁剪本身是一个可以讲的产品决策。

### 3.4 豁免规则库（差异化设计）

单独建一张豁免表，这是本项目区别于普通"敏感词过滤"的关键：

```json
{
  "exemption_id": "EX-ADLAW-9-3-2",
  "applies_to_category": "C2.7",
  "basis": "《广告绝对化用语执法指南》(2023)",
```

### 4.1 已核实的数据源

### 4.2 评测集 Schema

```json
{
  "sample_id": "EVAL-0001",
  "text": "本基金采用科学配置策略，预期年化收益率可达8%，本金无忧，欲购从速。",
  "text_source": {
    "type": "extracted_from_penalty",
    "doc_no": "〔2025〕40号",
    "issuer": "证监会山东监管局",
    "party": "利得资本管理有限公司",
    "url": "",
    "fetched_at": "",
    "verbatim": true
  },
  "spans": [
    {
      "span_id": "S1",
      "start": 14,
      "end": 24,
      "surface": "预期年化收益率可达8%",
      "label": "violation",
      "category": "C2.5",
      "severity": "high",
      "violated_clauses": ["PRIV-REG-6-4", "YF2019-316-3-5"],
      "rationale": "向投资者宣传预期收益率，构成变相承诺收益"
    },
    {
      "span_id": "S2",
      "start": 25,
      "end": 29,
      "surface": "本金无忧",
      "label": "violation",
      "category": "C2.1",
      "severity": "high",
      "violated_clauses": ["PRIV-REG-6-4"],
      "rationale": "明示保本"
    }
  ],
  "doc_label": "violation",
  "label_source": "regulator",
  "annotator": "primary",
  "annotated_at": "",
  "recheck": {"done": false, "agreed": null, "rechecked_at": ""},
  "notes": ""
}
```

**关键设计：以 span（文本片段）为标注和评测单位，不是整篇。** 理由：整篇级标注只能算文档分类准确率，无法评估"定位能力"，而定位能力恰恰是合规专员最需要的（他要知道**哪一句**违规）。span 级标注成本更高，但评测结论更硬。

**`label_source` 字段是标注可信度的核心标记**，取值 `"regulator"`（违规认定直接来自监管文书，可核查文号）或 `"annotator"`（由标注者依据法规条文自行判定）。两类样本在评测报告中必须分开统计——详见 §4.4 第一层。`recheck` 记录 §4.4 第二层的自重标结果。

`verbatim: true` 表示该文本是处罚决定书原文照录；若为忠实转写或拼接，必须标 `false` 并在 `notes` 说明。**禁止把改写过的文本标为 verbatim。**

### 4.3 标注规范

1. **标注对象**：只标"营销宣传文本中的违规表述"，不标处罚决定书里的监管叙述文字。
2. **span 边界**：取最小完整违规语义单元。"预期年化收益率可达8%"整体为一个 span，不拆成"预期年化收益率"和"8%"。
3. **severity 三档定义**：
   - `high`：触及保本保收益承诺、虚假数据、绝对化用语等硬性禁令，法规明文列举，无豁免空间。
   - `medium`：需要语境判断的隐性违规，或存在豁免可能的绝对化用语。
   - `low`：形式瑕疵（风险提示不显著、业绩登载格式不规范）。
4. **不确定即记录**：拿不准的样本放入 `data/eval/disputed.jsonl`，不进主评测集，但要保留——这些是后续写"标注局限性"章节的素材。
5. **一个 span 可挂多条 violated_clauses**（如同时违反 316 号文和私募规定第六条）。

### 4.4 标注质量控制

**单人标注的评测集，面试官可以合理质疑"你的标注就是标准答案吗"。** 本项目有三层应对，**前两层不依赖找任何人**：

**第一层（最强）：标注锚定监管认定，而非个人判断。**

违规样本抽取自行政处罚决定书、行政复议决定书、中基协纪律处分决定书。**"这段表述构成违规"这个判断是监管机关作出的，不是标注者作出的**——决定书里写明了违规事实和所违反的条款。标注者做的工作是"定位违规文本片段 + 对齐到 §3.2 taxonomy 的哪一类"，而不是"裁定它是否违规"。

因此评测集须区分并分别统计两类样本：

| 标签来源 | 含义 | 可信度 |
|---|---|---|
| `label_source: "regulator"` | 违规认定直接来自处罚/复议/纪律处分文书 | **高**——有外部权威依据，可逐条核查文号 |
| `label_source: "annotator"` | 由标注者依据法规条文自行判定（主要用于合规负样本与部分对抗样本） | 中——需第二、三层支撑 |

报告里如实给出两类占比。**`regulator` 类占比越高，评测集越硬。** 这也反过来强化了 §4.1 优先从 D1/D2/D4 取样的理由。

**第二层：时间间隔自重标（intra-rater reliability）。**

- 完成主标注后**间隔不少于 7 天**，从 `label_source: "annotator"` 的样本中随机抽 30 条（或全部，取小者），**不看第一次的结果**重新标注一遍。
- 计算 span 级 label 一致率与 category 一致率。
- 不一致的样本逐条复盘，修正标注规范中导致歧义的表述，并记录到 §4.3。
- 这一层测的是"你自己的判断是否稳定"。它弱于双人交叉标注，但**它诚实、可自足完成，且能暴露标注规范本身的模糊之处**——后者往往才是分歧的真正来源。

**第三层（可选，能做到就做，做不到不影响项目成立）：**

若恰好有同学愿意按 §4.3 规范独立标 30 条，则加算 inter-rater 一致率并一并报告。**不得把项目进度或评测有效性建立在这一层上。**

**报告措辞**（如实、不夸大）：

> "本评测集 {N} 条样本中，{R}% 的违规标签直接锚定监管文书认定（可逐条核查文号），其余 {A}% 由标注者依据法规条文判定。对后者执行了间隔 7 天的自重标校验，span 级 label 一致率 {待测}%，不一致样本的规范修正记录见附录。标注局限：单标注者，未做双人交叉验证。"

**主动写出"单标注者，未做双人交叉验证"这句局限性，比藏起来更有说服力。**

### 4.5 样本配比目标

| 类别 | 目标条数 | 下限（触发 §10 压缩） | 来源 |
|---|---|---|---|
| 违规样本（C2 为主） | 60–90 | 40 | D1 D2 D4 处罚/复议/纪律处分决定书原文抽取 |
| 违规样本（C1 C3 C4 C5） | 20–30 | 12 | 同上 |
| **对抗样本**（表面合规实质违规 / 表面违规实质合规） | 15–25 | **12（不可再降）** | D2 行政复议决定书为主，含豁免情形 |
| 合规负样本 | 40–60 | 25 | D6 已公开发布的产品宣传页 |
| **合计** | **135–205** | **89** | |

§1.4 与 §10 中"≥120 条"是**目标线**，"89 条"是**触发压缩方案的下限**——低于 89 条说明 §4.6 的数据源方案需要重做，而不是硬着头皮出报告。

对抗样本占比刻意拉高到 10%+，因为它是区分"纯规则"和"双轨引擎"效果的关键——纯规则在对抗样本上必然大量失分，这正是消融实验要证明的事。**对抗样本的下限之所以"不可再降"，是因为砍掉它就等于砍掉了本项目最主要的论证。**

### 4.6 第 1 周强制前置：抓取可行性试探

**不要一上来就承诺 150 条。** 第 1 周前 3 天先做一次 de-risking：

- 目标：手工 + 半自动获取 **20 份**处罚/复议决定书，跑通"检索 → 下载 → 抽取违规表述 → 结构化入库"全链路。
- 需要实测并记录的障碍：
  - 官网是否有反爬 / 频率限制 / 验证码
  - 正文是 HTML 还是扫描版 PDF（扫描件需要 OCR，成本陡增——若占比高，需调整数据源优先级）
  - 违规表述在决定书中的定位难度（有些决定书只写"存在违规宣传行为"而不引用原文，这类**不可用**，必须弃掉）
  - 单份文书的平均处理耗时
- **决策门**：若 20 份中「含可直接引用的违规表述原文」的比例 < 40%，或单份处理耗时 > 30 分钟，则触发方案调整：
  - 备选 A：降低评测集目标至 80 条，提高每条质量
  - 备选 B：主力数据源从 D3（各地证监局，结构不统一）转向 D4（中基协，格式相对统一）
  - 备选 C：改用 D5 市场监管总局典型案例（结构化程度高，但偏通用广告、金融属性弱）

这个决策门写进计划，是为了避免第 3 周才发现数据拿不到、整个项目返工。

### 5.2 模块边界

每个模块回答三个问题：做什么、怎么用、依赖什么。**核心约束：UI 和评测流水线只依赖 `AuditOrchestrator` 的公开接口，不碰任何内部模块。** 这样换 UI（Streamlit → FastAPI+React）或换检索实现都不影响其他部分。

| 模块 | 做什么 | 接口 | 依赖 |
|---|---|---|---|
| `ContentAdapter` | 把 txt/md/粘贴文本统一成 `AuditRequest`。为未来 OCR/ASR 预留扩展点 | `load(source) -> AuditRequest` | 无 |
| `RegulationKB` | 加载条款库、禁用词库、豁免库；提供按 category 检索条款 | `search(query, categories) -> list[Clause]`；`lexicon(category) -> list[str]` | 条款 JSONL 文件 |
| `Retriever`（接口） | 给定文本片段，返回相关条款。**两个实现可切换** | `retrieve(text, top_k) -> list[Clause]` | `RegulationKB` |
| `RuleEngine` | 轨道 A。词库/正则匹配，输出候选 span 及其命中词、Tier、是否需语义判断 | `scan(text) -> list[RuleHit]` | `RegulationKB.lexicon` |
| `LLMReviewer` | 轨道 B。带检索到的条款与豁免提示，让 LLM 输出结构化判定 | `review(text, rule_hits, clauses) -> list[LLMFinding]` | LLM Client、`Retriever` |
| `LLMClient` | 封装 OpenAI 兼容 API 调用，含重试、超时、token 计量 | `complete(messages, schema) -> Parsed` | `openai` SDK |
| `RiskAggregator` | 融合两轨结果，去重/合并重叠 span，定 severity，输出三级分档 | `aggregate(rule_hits, llm_findings) -> AuditResult` | 无 |
| `Rewriter` | 对每个违规 span 生成合规改写建议 | `rewrite(text, span, clause) -> Suggestion` | `LLMClient` |
| `FeedbackStore` | 落盘人工纠偏记录（误报/漏报标记），可导出为规则库与提示词迭代素材 | `record(feedback)`；`export(path)` | JSONL 文件 |
| `AuditOrchestrator` | 编排全流程，是唯一对外门面 | `audit(request) -> AuditResult` | 上述全部 |

### 5.3 数据流（一次审核的完整调用链）

```
1. UI 收到用户粘贴的文案
2. ContentAdapter.load() → AuditRequest{text, meta}
3. RuleEngine.scan(text) → list[RuleHit]
     ├─ Tier1 命中（保本/零风险/稳赚不赔…）→ 直接标 severity=high，needs_llm=False
     ├─ Tier2 命中（国家级/最佳/第一…）  → 标 needs_llm=True，附豁免提示
     └─ Tier3/4 命中（安全/高收益/欲购从速…）→ 标 severity=medium，needs_llm=True
4. Retriever.retrieve(text, top_k) → 相关条款（最多 K 条）
5. 分支判断：
     ├─ 若无任何 needs_llm=True 的命中，且 char_count(text) < SHORT_TEXT_LIMIT → 跳过 LLM
     │    （SHORT_TEXT_LIMIT 为配置项，默认 200 字符，写入 configs/*.yaml，可调；
     │      其取值对结果的影响须在 §7.3 消融中作为一组参数扫描报告，不得默默硬编码）
     └─ 否则 → LLMReviewer.review(text, rule_hits, clauses) → list[LLMFinding]
6. RiskAggregator.aggregate(rule_hits, llm_findings)
     ├─ 合并重叠 span（IoU > 0.5 视为同一处）
     ├─ severity 取两轨较严者
     ├─ 冲突时（规则说违规、LLM 说豁免）→ 降级为 medium，转人工复核，并在 rationale 记录分歧
     └─ 计算文档级结论：red / yellow / green
7. Rewriter.rewrite() 对每个 severity>=medium 的 span 生成改写建议
8. AuditResult 返回 UI，渲染高亮 + 条款悬浮 + 改写按钮
9. 用户点"这是误报" → FeedbackStore.record()
```

第 6 步的**冲突降级规则**是有意设计：规则和 LLM 判定不一致时，系统不擅自选边，而是升级给人工，同时把分歧原因写进 rationale。这让 Human-in-the-Loop 不只是"高危转人工"，而是"任何不确定性都转人工"。

`detected_by` 与 `agreement` 两个字段是消融实验的数据基础——有了它们，评测时能直接算出"规则独立贡献""LLM 独立贡献""两者一致率"，不需要重跑系统。

## 6. 双轨引擎设计

### 6.1 轨道 A：规则引擎

词库分四层，**每个词条都必须带 `source_clause_id`，禁止无出处的自造词**：

| Tier | 语义 | 示例词条（均来自法规原文，见 §3.1 R5/R7） | 处理 |
|---|---|---|---|
| **T1 硬性红线** | 法规明文禁止，无豁免空间 | 保本、保收益、零风险、无风险、本金无忧、稳赚不赔、躺赚、承诺收益、固定收益、预期收益率、目标收益率、基准收益率、净值归一 | 直接 `severity=high`，`needs_llm=False` |
| **T2 绝对化用语** | 原则上禁止，**但有法定豁免** | 国家级、最高级、最佳、最好、最优、最强、第一、唯一、独一无二、顶级、极品、至尊、王牌、销量第一 | `needs_llm=True`，附 §3.4 豁免提示 |
| **T3 夸大误导** | 语境依赖强 | 安全、保证、承诺、保险、避险、有保障、高收益、坐享财富增长、安心享受成长、尽享牛市、业绩稳健、业绩优良、名列前茅、位居前列 | `severity=medium`，`needs_llm=True` |
| **T4 营销施压** | 片面强调时间限制 | 欲购从速、申购良机、限时抢购、最后 N 天 | `severity=medium`，`needs_llm=True` |

**T2 是整个双轨设计的枢纽。** 正因为《广告绝对化用语执法指南》给了三种豁免，T2 命中不能直接判违规，必须交给 LLM 结合语境判断——这是"为什么需要双轨"的法规级论证，不是工程炫技。

实现要点：
- 中文分词用 `jieba`（需 `pip install jieba`，纯 Python，轻量）。T1/T3/T4 用精确词匹配 + 简单正则；T2 用正则允许"最X""第一X"等变形。
- 需处理的变形：谐音（"保本"→"宝本"）、拆字、中间插符号（"稳*赚*不*赔"）、全半角、繁简。**MVP 只做全半角与繁简归一 + 插入符号剥离**，谐音与语义变形交给 LLM 轨（这本身是分工论证的一部分）。
- 规则库以 YAML/JSONL 存盘，热加载，改词库不需要改代码——这对应面试官问的"监管政策变了怎么快速响应"。

### 6.2 轨道 B：LLM 语义审核

**提示词结构**（分段，便于消融时逐段拆除）：

```
[角色] 你是金融机构的合规审核专家。
[任务] 审核以下营销文案是否违反中国金融营销宣传法规。
[法规上下文] {检索到的条款原文，含 clause_id 与 source_no}
[豁免规则] {命中的豁免条款与 decision_hint}
[规则轨线索] {RuleEngine 的命中位置与 Tier，作为提示而非结论}
[输出契约] 严格输出 JSON，schema 为 {LLMFinding 的 pydantic schema}
[硬约束]
  - 每一条 finding 必须引用给定的 clause_id，禁止编造条款
  - 若给定条款不足以判定，输出 needs_human=true 并说明缺什么
  - 不得对未出现在文本中的内容做判定
[待审文案] {text}
```

关键工程决策：
- **结构化输出用 pydantic schema 校验**（`pydantic` 已装）。LLM 返回不合 schema 时重试 1 次，仍失败则降级为 `needs_human=true`，**绝不静默丢弃**。
- **条款引用做后置校验**：LLM 输出的每个 `clause_id` 必须在 `RegulationKB` 中真实存在，不存在则剔除该 finding 并记 warning。这是**防幻觉的硬性拦截**，不是靠提示词祈祷。面试问"大模型幻觉怎么办"，这就是答案，而且是代码级的答案。
- **规则轨线索作为提示而非结论**：告诉 LLM"规则在第 14–24 字命中了 T1 词'预期收益率'"，让它聚焦判断，但明确说明它可以推翻规则轨的判断（用于豁免场景）。

### 6.3 检索方案：三个选项与选型理由

这是本项目最需要讲清楚的技术选型，因为它是一个**主动拒绝业界标配**的决定。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 全量入 context** | 把所有条款原文一次性塞进提示词 | 零检索误差，实现最简 | 本项目条款总量约 100–300 条、几万字符，**其实塞得下**。但每次调用 token 成本高、延迟大，且无法回答"为什么引用了这一条" |
| **② 轻量检索（推荐）** | 违规类型 taxonomy 路由 + BM25/关键词打分，只注入 top-K 相关条款 | 成本低、延迟小、**检索结果可解释**（能说清为什么召回这条）、无额外依赖（jieba 即可） | 召回依赖 taxonomy 路由质量；语义近义表述可能漏召 |
| **③ 向量检索 RAG** | embedding + 向量库（chromadb/faiss） | 业界标配，语义召回强，简历上"有 RAG" | 对本项目几百条法条属于**过度设计**；需额外安装向量库与 embedding 模型；引入 embedding 质量这个新的不可控变量；**且无法解释召回原因** |

**选型：② 为默认实现，但 `Retriever` 做成接口，③ 作为可选实现。**

理由与话术：本项目法规语料仅数百条，向量检索的核心优势（大规模语料的语义召回）在此规模下无法体现，而它的成本（额外依赖、embedding 质量不可控、召回不可解释）是实打实的。因此默认用 taxonomy 路由 + BM25，把"可解释性"和"零依赖"拿到手。同时 `Retriever` 是接口，法规库扩展到上千条或多法域时，换成向量实现不需要改动 `LLMReviewer`。

**面试价值**：能说出"我知道 RAG 是标配，但我评估后认为在这个语料规模下它是过度设计，我的判断依据是 X，架构上我预留了切换点 Y"——这比"我用了 RAG"值钱得多。AI PM 岗最看重的就是这种判断力。

**评测验证**：§7.3 的消融实验会加一组 `②vs③` 对比。若数据显示向量检索召回率显著更高，就采纳它并如实修改本节结论。**先写判断，再用数据检验判断**，这本身就是方法论。

### 6.4 融合与风险分级

| 文档级结论 | 触发条件 | 系统行为 |
|---|---|---|
| 🔴 **red（高危拦截）** | 存在任一 `severity=high` 且 `agreement != "conflict"` 的 finding | 阻断发布，必须人工确认后才能放行 |
| 🟡 **yellow（人工复核）** | 存在 `severity=medium`，**或**两轨判定冲突，**或** LLM 返回 `needs_human=true`，**或** LLM 置信度低于阈值 | 允许提交但打黄标，进人工队列 |
| 🟢 **green（放行）** | 无 finding，或仅 `severity=low` | 放行，低危项仍展示供参考 |

**阈值不拍脑袋定**：LLM 置信度阈值在评测集上用 §7.2 的加权成本函数扫描选取，选取过程与结果写进评测报告。

**冲突降级规则**（重要）：规则说违规、LLM 说豁免（或反之），一律降为 `yellow` 转人工，`rationale` 中写明双方判断与依据。系统不擅自选边。

### 6.5 Auto-Fix 改写

- 输入：原文 + 违规 span + 命中条款原文 + 豁免提示
- 输出：改写后的完整句子 + `rewrite_note`（说明改了什么、为什么）
- **约束**：改写必须保留原营销意图的合规表达方式，不得简单删除。"预期年化收益率可达8%" → "历史业绩不代表未来表现，投资有风险"，而不是把整句删掉。
- **改写结果也要过一遍审核**：改写后的文本重新走 `RuleEngine`（不走 LLM，省成本），若仍命中 T1 则标记"改写失败，需人工撰写"。**这是一个容易漏掉但很能体现产品思维的闭环。**
- MVP 不做批量改写、不做多候选方案。

### 6.6 错误处理与降级

| 故障 | 系统行为 | 用户可见 |
|---|---|---|
| LLM API 超时 / 5xx | 指数退避重试 2 次 | 重试中提示 |
| 重试后仍失败 | **降级为纯规则模式**，文档级结论强制 `yellow`，绝不给 `green` | 明确横幅："语义审核不可用，当前为纯规则结果，所有内容须人工复核" |
| LLM 返回不合 schema | 重试 1 次 → 仍失败则 `needs_human=true` | 该项标"AI 无法判定" |
| LLM 引用了不存在的 clause_id | 剔除该 finding，记 warning 到日志 | 不展示（静默），但日志可查 |
| API key 缺失 / 额度耗尽 | 启动时即失败，报错明确指出 | 阻止启动，不允许静默跑成纯规则 |
| 输入文本超长 | 分段审核，分段结果合并 | 展示分段进度 |

**降级的核心原则：宁可误报，不可漏放。** 任何不确定性都收敛到 `yellow`（人工复核），绝不收敛到 `green`。这条原则要写进 PRD，也是面试回答"AI 出错谁负责"的产品化答案。

### 6.7 性能策略（回答"高并发实时性"问题）

不实现消息队列，但要有**实测数据**支撑回答：

1. **分级处理**：T1 硬红线由规则层毫秒级拦截，不进 LLM。评测时统计"规则层独立拦截占比 {待测}%"，这个数字直接支撑"规则层过滤掉大部分流量"的论述。
2. **短路优化**：无任何 `needs_llm` 命中且文本较短时跳过 LLM 调用。统计"跳过率 {待测}%"。
3. **异步改写**：Auto-Fix 不阻塞审核结论返回，先出结论再补改写建议。
4. **实测延迟**：报告 P50 / P95 端到端延迟，以及规则层单独延迟（应为毫秒级）。
5. **实测成本**：每篇平均 input/output tokens 与人民币成本，推算"日均 N 篇的月成本"。

有这五个数字，性能问题就能用数据回答，而不是背架构名词。

## 7. 评测方案

> **这一节产出简历上的所有数字。它的严谨程度决定项目的可信度上限。**

### 7.1 指标定义

**span 级匹配规则**：预测 span 与标注 span 的字符区间 IoU ≥ 0.5 视为匹配成功；匹配后还需 `category` 一致才计入"完全正确"。分别报告"位置匹配"和"位置+类别匹配"两套指标，避免用宽松口径美化结果。

| 指标 | 公式 | 说明 |
|---|---|---|
| Precision | TP / (TP + FP) | 系统报出的违规里有多少是真的 |
| Recall | TP / (TP + FN) | 标注的违规里系统找到了多少 |
| F1 | 2PR / (P + R) | 综合 |
| **误报率 FPR** | FP / (FP + TN) | **合规专员视角的核心指标**：合规内容被误拦的比例，直接对应"人工复核工作量" |
| 漏报率 FNR | FN / (FN + TP) = 1 − Recall | |
| **高危召回率** | Recall(severity=high) | **单独统计，不可与整体 Recall 混谈**。漏放一条"保本承诺"的业务后果远大于漏放一条"欲购从速" |
| 文档级准确率 | 文档 verdict 与标注 doc_label 一致的比例 | 对应"整篇能不能放行"的实际决策 |
| 标注可信度 | `label_source=regulator` 占比 + 自重标一致率（见 §4.4） | 标注质量证明 |

### 7.2 业务代价加权（关键设计）

漏报与误报的业务代价**严重不对称**：漏放一条保本承诺可能导致监管处罚（真实案例中罚款达 310 万元），误报一条只是多花合规专员几十秒。因此不能用 F1 作为唯一优化目标。

定义加权成本：

```
Cost = α·FN_high + β·FN_medium + γ·FN_low + δ·FP
建议初值 α=10, β=3, γ=1, δ=1
```

- 所有 severity=high 的阈值选择、置信度阈值扫描，**以最小化 Cost 为目标，而非最大化 F1**。
- α/β/γ/δ 的取值必须在报告中说明依据，并做**敏感性分析**：α 从 5 变到 20 时最优阈值如何移动。
- 敏感性分析能挡掉"你的权重是拍的吧"这个质疑——答案是"是拍的，但我验证了结论对权重不敏感"或"在这个区间内敏感，所以我选了保守侧"。

### 7.3 消融实验设计

七组对照，逐层加入组件，用数据论证每个架构决策（E5 为可选，见 §10 可压缩项）：

| 实验 | 配置 | 验证什么 |
|---|---|---|
| **E0** | 纯规则，四 Tier 命中即判违规，无豁免逻辑 | 基线。预期：召回尚可、**FPR 极高**（痛点一的量化证据） |
| **E1** | 纯规则 + 豁免白名单（硬编码豁免短语） | 白名单能救回多少误报？预期：有限，因为豁免是语境依赖的 |
| **E2** | 纯 LLM，zero-shot，不注入任何法规 | LLM 的先验知识够不够？预期：类别判定混乱，条款引用不可靠 |
| **E3** | LLM + 全量法条入 context | 检索方案 ① |
| **E4** | LLM + 轻量检索（方案 ②） | **检索方案选型的关键对比** |
| **E5** | LLM + 向量检索（方案 ③，可选实现） | 若 E5 显著优于 E4，则修改 §6.3 结论 |
| **E6** | **完整双轨系统**（规则前置 + 检索 + LLM + 融合分级 + 冲突降级） | 最终方案 |

每组报告：Precision / Recall / F1 / FPR / 高危 Recall / **Cost** / 平均 token / 平均成本 / P50 与 P95 延迟。

**特别关注 E0 → E6 在对抗样本子集上的表现差异**（§4.5 中刻意拉高占比的那 15–25 条）。这是最能体现双轨价值的切片，要单独出一张表。

### 7.4 可复现性要求

- `eval/run_eval.py --config configs/e6.yaml` 一键跑完单个实验
- `eval/run_all.sh` 跑完 E0–E6，输出 `eval/results/metrics.json` + `eval/report.md`
- **固定随机性**：LLM `temperature=0`；记录 model 名称与版本、API base_url、提示词版本号（git commit hash）
- **缓存原始响应**：每次 LLM 调用的 request/response 落盘到 `eval/cache/`，重跑评测时可 replay，避免重复花钱、也保证数字可追溯
- **数据集冻结**：评测集一旦用于出报告就打 git tag（如 `eval-v1.0`），报告中的数字绑定该 tag。**之后修改标注必须升版本号并重跑全部实验**——不允许"改标注把数字改好看"
- README 写明复现步骤与预期耗时、预期 API 花费

### 7.5 评测报告结构

`eval/report.md` 应包含：数据集构成与来源统计 → 标注方法与一致性 → 指标定义 → E0–E6 主表 → 对抗样本切片表 → 分 category 表现表（暴露系统在哪类弱）→ 加权成本与敏感性分析 → 成本与延迟 → **失败案例分析（至少 5 个，逐个讲清为什么错）** → 局限性与未来工作。

**失败案例分析这一节是面试金矿。** 大部分候选人只会讲系统多准，讲不清"它在哪种情况下会错、为什么错、我怎么兜底"。能主动讲失败案例，是产品成熟度的强信号。

### 7.6 预注册（防止事后合理化）

**在跑评测之前**，先在 `eval/PREREGISTRATION.md` 写下：

- 主指标是什么（建议：高危 Recall + Cost）
- 判定"双轨优于纯规则"的具体阈值（如：Cost 降低 ≥ 30% 且高危 Recall 不低于 E0）
- 若结果不达预期怎么办（如实报告 + 分析原因，**不调指标口径来让结果好看**）

预注册这件事本身就可以写进简历和面试：它证明你的数字不是挑出来的。

### 8.2 高亮溯源

- 违规 span 在原文中按 severity 着色：红/黄/灰（低危）
- 点击高亮 → 右侧滚动定位到对应 finding
- 点击 finding → 原文对应 span 闪烁
- **条款引用可点击展开原文**，并显示 `source_no` 与官方 URL（若有）。这是"有法可依"的可视化证据，也是演示时最有说服力的一刻
- 冲突项用特殊标记（⚠️）并明确写出双方判断，不隐藏分歧

### 8.3 HITL 纠偏闭环

用户每次点击 `[标记为误报]` / `[确认违规]`，落盘一条记录：

```json
{
  "feedback_id": "FB-0001",
  "request_id": "req_20261016_001",
  "finding_id": "F3",
  "system_verdict": "medium",
  "system_category": "C2.9",
  "detected_by": ["rule"],
  "human_action": "false_positive",
  "human_category": null,
  "human_note": "属常规营销表述，未构成片面强调",
  "reviewer": "demo",
  "ts": "2026-10-16T14:20:00+08:00"
}
```

- 纠偏队列页面：按 category 聚合统计误报数，暴露"哪类规则最容易误杀"
- **导出为迭代素材**：`FeedbackStore.export()` 输出可直接用于补充豁免库 / 调整提示词的结构化数据
- **闭环验证（可选加分项）**：把纠偏记录补充进豁免库后重跑评测，报告 FPR 是否真的下降。**若能做出这一步，"数据闭环"就不是 PPT 词汇而是可验证的事实**——这是简历上很硬的一条

### 8.4 审核报告导出

Markdown 报告含：文案摘要、文档级结论、逐条 finding（含 span 原文、类别、条款引用、改写建议）、免责声明、系统版本与提示词 commit hash、生成时间戳。

**免责声明必须出现在每一份导出报告里**，措辞见 §5.4 `disclaimer` 字段。这不是形式合规，是产品定位的书面固化。

## 关于实施计划的说明

本项目跨 12 周、6 个阶段，**不适合一次性写成一份从头到尾的实施计划**——P1 的产出（§4.6 抓取试探报告）会直接改变 P1.5 的目标，P3 的评测结果可能推翻 §6.3 的检索选型结论。

建议的实施计划切分：

- **计划 1（先写这个）**：P0 前置 + P1 数据地基，终止于 §4.6 的 go/adjust 决策门。
- **计划 2**：P1.5 数据补全 + P2 引擎，终止于 CLI 能输出符合 §5.4 Schema 的结果。
- **计划 3**：P3 评测（含预注册文档先行）。
- **计划 4**：P4 产品化 + P5 面试弹药。

每份计划独立评审、独立验收。这样任何一个决策门触发调整时，只需要重写后续计划，不会推翻已完成的工作。
